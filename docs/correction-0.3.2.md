# 0.3.2 本地纠错修复

日期：2026-11-21。修复短句返回 `invalidResult` 及同段重复指代漏改，公共 `TextCorrecting` / `CorrectionRequest` / `CorrectionCandidate` 接口保持不变。

## 根因与行为

当前固定的 llama.cpp completion 引擎在每个逻辑 batch 之后检查结束标记，包含提示词预填充阶段。原来 batch 为 128，ChatML 的结束标记落在提示词分批边界时，可能尚未读完整个提示就结束，只输出结束标记。现在逻辑 batch 覆盖整个受限上下文，物理 microbatch 仍为 128；请求 JSON 键顺序固定，避免相同输入产生不同提示布局。

完整文本生成还可能漏改后文同一错误，并在长文本中截断。现在模型只输出简短分析和 `edits: [{from, to}]`。基础层用纯函数对照原文应用局部修改：相同短语一次覆盖所有匹配，不级联替换；重复相同建议去重，冲突和交叉重叠拒绝。模型建议中找不到的原文片段忽略，完整短语优先于被其包含的短词。含歧义的重复单字替换拒绝。

业务层在第一轮有实际修改时，最多再复核一次，补查后文漏改；两轮共用默认 45 秒预算。第二轮失败保留已校验的首轮候选，取消始终向上传播。这里的校验确认修改有原文依据与合法结构，不证明语义一定正确。

提示词检查整段动作对象及指代，只在配送主题出现时增加配送提示；正常接送人的表达需要保留。数字、币种、否定词和事实要求保持，候选仍供用户核对。错误界面显示中文原因，保留原始转写。

## 资源边界与验证

输入正文最多 3000 UTF-8 字节、词汇最多 1000 字节；上下文 4096 或 8192 token，输出预算为 `max(768, 正文字节数 + 256)`，最大 3256 token。单轮生成最多 16 项修改，解析结果最多 16384 字节，候选最多 6000 字节。逻辑 batch 不改变物理 microbatch 大小。

有效 RED 包括提示预填充参数、局部修改、重复建议、复核漏改、陈旧建议、包含短语、主题隔离、初始超时和可读错误。对应本地记录为 `.build/llm-prefill-red.log`、`llm-edits-red.log`、`llm-identical-edits-red.log`、`llm-review-red.log`、`llm-stale-review-red.log`、`llm-enclosing-edits-red.log`、`llm-domain-isolation-red.log`、`llm-initial-budget-red.log`、`llm-user-errors-red.log`。编译或环境失败未计为 RED。

最终 Swift 84 个测试通过，行覆盖率 97.80%，基础层 100%；Python 2 个协议测试通过，97.78%。真实 Qwen 6 个 E2E 和打包资源相同 6 个 E2E 分别通过，另验证了两种用户反馈短句，私有正文不提交。完整统计与复现方法见[报告](reports/0.3.2/README.md)。尚无准确率基准，不把这些回归通过作为通用语义正确率保证；AirPods、16GB/8GB 和长期性能仍待验收。

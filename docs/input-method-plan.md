# 语音与手势输入法方案

日期：2026-11-21。状态：macOS [Demo 0.3.2](demo.md) 默认使用 Qwen3-ASR-1.7B 4-bit，并接入 Qwen3-4B 录音中纠错；保留 Whisper 替换引擎、API 与 CLI。真实中英文、双模型链路与打包资源 E2E 已通过；Watch、系统输入法与整体性能验收待实施。历史基础实现见 [切片 1](acceptance-01.md)。

工程约束见 [开发规范](../AGENTS.md)，测试与覆盖率要求见 [测试标准](testing.md)。

## 产品目标与范围

AirPods 负责收音，Apple Watch 负责控制，目标设备负责语音识别、候选展示与文字输入。目标体验为：开始一轮输入 → 说话 → 停止 → 上下切换候选项 → 确认写入当前输入框。

首发输入设备尚未确定。Mac 跨 App 输入是已提出的优先验证建议，不作为用户已经选定的平台。iPhone/iPad 自有 App 输入与跨 App 键盘输入分别评估，不承诺两端首版同时交付。

离线识别与中文、英文输入是明确要求。候选项如何产生、是否包含改写或纠错仍待确定；这些设计不得使基本输入依赖云端。候选切换和输入编排可以先使用显式标记的合成数据独立验证。

## 离线与语言要求

- 模型和必要资源可预先下载或随安装包提供；安装完成后，录音、识别、候选选择和确认写入不依赖互联网，也不上传音频或识别正文。
- 离线指不依赖互联网或云端服务，设备间控制仍可使用蓝牙或本地网络；真实 E2E 应断开互联网，同时保留必要的本地设备链路。
- 必须支持中文和英文分别输入。将中英混说作为重点验收场景，例如“这个 API 用 RxSwift 实现”，单独记录英文术语、专名、数字和标点的识别效果；支持两种语言不直接证明混说效果。
- 使用原语言转写，不默认将中文翻译为英文，或将英文术语改写成中文。语言自动识别、手动选择和混说策略在本地识别接口中明确。
- 模型未安装、文件损坏或设备不支持时，明确报告不可用原因，不静默切换云端识别。断网冷启动也必须能够加载已安装模型。

## 本地 STT 评估

当前 Demo 按用户最新决定使用 Qwen ASR；以下保留可替换引擎及评估范围，不代表真机准确率和完整平台选型已经验收。

| 候选 | 本项目评估定位 | 能力依据与待验证项 |
|---|---|---|
| Whisper 多语言模型 + whisper.cpp | 若先做 Mac，首轮评估以 large-v3-turbo 为基线；资源受限设备再对比 small 等多语言模型 | [Whisper](https://github.com/openai/whisper)提供多语言转写模型；[whisper.cpp](https://github.com/ggml-org/whisper.cpp)支持本地推理及 Apple Silicon 优化。不要使用仅英语的 `.en` 模型；需实测中文、英文和混说，以及分段、结果修订、内存和延迟 |
| Qwen3-ASR 1.7B 4-bit | Demo 0.3.2 默认 STT，MLX Audio 适配已运行 | [官方仓库](https://github.com/QwenLM/Qwen3-ASR)与 [MLX Audio](https://github.com/Blaizzy/mlx-audio)；当前使用常驻模型的周期性重识别，尚未接原生流式解码，轻声与混说需单独评估 |
| Apple SpeechTranscriber | 支持设备上的系统本地识别对照 | [系统接口](https://developer.apple.com/documentation/speech/speechtranscriber)要求检查设备及语言资源支持；[Apple 说明](https://developer.apple.com/videos/play/wwdc2025/277/)确认端上识别。需验证中英文资源、混说、断网冷启动和系统版本兼容，不将选择某个 locale 等同于自动双语 |

使用同一批真实 AirPods 录音对比候选：中文 CER、英文 WER、混说及术语正确率、首个可用结果延迟、停止到最终文本的延迟、冷/热启动、峰值内存、能耗和静音误识别。模型、量化、推理引擎、设备和系统版本随报告记录；达标阈值在首轮实测后确定。

识别模块保持可替换，接口区分临时结果、最终结果、错误和取消；简单单次识别可以直接使用原生异步调用，多事件交错协调时才采用 Rx*。

## 内存与性能预算

明确要求：承载本地推理的设备在 **16GB 总内存配置**上可运行，整个输入法的**峰值内存不超过 8GB**。统计包含应用、辅助推理进程、两模型、推理缓存和音频缓冲，不仅计算模型文件；不将模型放入不同进程作为绕过上限的方法。

当前组合为 Qwen3-ASR-1.7B 4-bit + Qwen3-4B-Instruct-2507 Q4_K_M，LLM 上下文按输入限制为 4096 或 8192 token、输出 768–3256 token；模型生成局部修改，首轮有实际修改时最多再复核一次，两轮共用默认 45 秒预算。模型磁盘大小分别约 1.60GB / 2.50GB，不以此推算运行内存。M5 Pro / 48GiB 的短录音双模型 E2E 采样到进程树 `ri_phys_footprint` 峰值约 2.40GiB（0.3.2 源码及打包资源回归）；这是初测，尚未验证 16GB 配置、长输入、连续轮次、文件映射占用、内存压力或 swap。详见 [Demo 记录](demo.md)。

下面保留原 Whisper + Qwen 短上下文组合的历史估算，不能套用为当前 Qwen ASR 组合的实测结论。

| 部分 | 文件大小参考 | 运行内存预算（估算） |
|---|---|---|
| Whisper turbo Q5_0 | 547 MiB，约 0.57GB | 约 1–2GB |
| Qwen3-4B-Instruct-2507 Q4_K_M | 约 2.5GB | 约 3–4.5GB |
| 应用、音频和控制链路 | 不作为模型文件统计 | 约 0.3–0.5GB |

文件大小分别依据 [whisper.cpp 模型列表](https://github.com/ggml-org/whisper.cpp/blob/master/models/README.md)和 [Unsloth 量化文件列表](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-GGUF/tree/main)。运行数字由权重、短上下文缓存和运行时开销估算；整体先按约 **5–7GB** 预留，必须通过目标设备实测确认 8GB 峰值门槛。内存计量统一单位，使用平台工具核对物理占用，避免重复累加共享 CPU/GPU 缓冲；不以持续 swap 掩盖资源不足。

- 限制上下文、输出长度、音频缓冲和队列容量；不使用模型的最大上下文作为默认纠错窗口，不无限保留历史或 KV 缓存。
- ASR 在当前会话常驻；LLM 按需加载并退出。录音中，文本稳定约 800ms 或持续变化约 3 秒时请求纠错，停止时立即补最终候选；相同文本去重，过期请求取消，不等待用户停止才纠错。
- 仅顺序执行推理不会释放常驻权重。按需卸载能降低驻留占用，但必须测量重新加载延迟及内存是否真正释放。
- 在接近预算或收到内存压力信号时，使用有界的降级策略，例如清理缓存、卸载纠错模型并保留原始识别结果；该策略必须经过测试，不将估算视为已实现的硬内存限制。
- 16GB 容量不代表吞吐或延迟达标。具体芯片尚未提供，当前不承诺 CPU/GPU 占用百分比、推理速度或响应秒数。
- 分别测量模型冷/热加载、STT 实时因子、停止到最终文本延迟、LLM 上下文处理与生成吞吐、纠错总延迟，以及连续使用的温升和能耗；端到端报告至少包含 p50/p95。性能目标在目标设备实测后确定，8GB 内存上限已是必选门槛。

## 交互基线

以下是待真机验证的设计，不代表系统已经提供完整手势能力。

| 输入阶段 | 动作 | 预期行为 |
|---|---|---|
| 空闲 | 双指互点两下 | 请求开始本轮录音；设备实际可采集后显示录音中 |
| 录音中 | 双指互点两下 | 停止采集，等待本轮识别结果 |
| 候选选择中 | 手腕上翻一次 | 选中上一个候选项 |
| 候选选择中 | 手腕下翻一次 | 选中下一个候选项 |
| 候选选择中 | 双指互点两下 | 请求将当前候选写入目标输入框 |
| 输入未提交时 | 取消按钮 | 停止本轮任务，丢弃未提交内容；迟到结果不得上屏 |

- “上翻/下翻”指腕部姿态变化，不是触摸屏滑动，也不是系统已经识别好的上下手势事件。
- 双指互点按当前状态映射到一个可见的主要按钮；不在同一个场景绑定多个主要操作。
- 上下切换仅在候选选择阶段生效。动作触发一次后需回到中立范围重新就绪，避免回程触发相反方向。
- 阈值、迟滞、中立区、时间窗口与左右手坐标校准由配置与实测确定，不在文档中伪造准确率或固定参数。
- 首版草案中，列表到达首尾后保持当前位置，不循环；没有候选项时不能确认。切换后可提供触觉反馈，效果待真机验证。
- 确认表示写入文字，不自动发送消息。写入失败保留候选与可重试状态；不把控制消息送达当成文字已写入。
- 提供屏幕按钮作为开始、停止、切换和确认的替代入口，便于调试和手势不可用时操作。

| 能力 | 公开接口依据 | 本项目必须验证 |

## 两层模块设计

以下为职责规划，不要求预先建立所有模块或空目录。

| 层 | 模块职责 | 公开边界 |
|---|---|---|
| 基础层 | 手势样本坐标归一、方向判定、迟滞和重新就绪规则 | 显式样本、时间值、配置和旧状态 → 新状态与动作值 |
| 基础层 | 候选列表校验、选择移动及首尾边界 | 不可变列表、当前选择与动作 → 新选择结果 |
| 基础层 | 输入会话状态转换 | 状态与事件 → 新状态和待执行命令值 |
| 基础层 | 命令值校验、身份和版本规则 | 输入值 → 有效值或明确错误；不执行通信 |
| 业务层 | 输入用例与多事件协调，需要时采用 Rx* | 输入命令、状态、操作结果与错误；需要流协调的接口明确其事件语义 |
| 业务层 | 音频采集及本地识别接入 | 本地模型就绪、可取消采集/识别操作、路由与识别结果事件 |
| 业务层 | Watch 动作采集与反馈 | Core Motion 样本流、系统互点操作和触觉执行 |
| 业务层 | 跨设备通信与文字写入 | 可达性、操作回执、目标输入会话和写入结果 |
| 业务层 | 应用装配与界面绑定 | 创建依赖、绑定可见控件并展示状态 |

基础层不认识 Rx、Core Motion 或音频设备对象。业务层将外部数据转换为值后调用纯函数，并在明确串行上下文中更新状态。接入与资源所有权留在业务层相应模块，逻辑层数保持为两层。

手势/点击、识别结果、取消操作和通信回执相互交错，需要组合、切换或竞态控制的流程采用 Rx*，具体库按实现语言选择。普通计算、简单顺序调用和单次异步操作使用普通函数或语言原生异步机制；业务层不统一要求使用 Rx*，模块接口也不全部流化。

跨设备协议在实现前定义命令身份、轮次、会话、版本、去重和过期规则。确认写入属于不可随意重试的动作，必须处理重复确认、目标焦点变化、回执丢失和执行结果未知，防止重复上屏或写入错误输入框。
